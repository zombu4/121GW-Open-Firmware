# Changelog of the 121GW Companion

What each release brought, newest first. The release page of a version shows only its own paragraphs.

New in 1.3.7: the current clamp of firmware 1.3.5 (F-1.35, GitHub issue 39). With a clamp ratio set on the meter (SETUP page CLP: 1 mV/A, 10 mV/A, 100 mV/A or 1 V/A), DCV, ACV, DCmV and ACmV show the clamp's current: the LIVE page, the statistics, the trend and recordings show A (or mA for small currents) with the point where the meter puts it, and OFL when the current does not fit the meter's five digits. METER SETTINGS has the row "Current clamp ratio" (firmware F-1.35 and newer).

New in 1.3.6: METER SETTINGS no longer fails with "the link is busy: settings" (GitHub issue 37). Since 1.3.4 the page reads the settings by itself when it opens and when the meter shows page Ld; when two of these reads met (on a meter with the old BLE112 Bluetooth module a read takes longer than the 2.5 s a second request waits), the second one failed. Now one settings read or write runs at a time, and a read that finds another one running waits for it and shows its result. The macOS installers are checked again when Apple's ticket service drops the connection during the check.

New in 1.3.5: the METER SETTINGS page has no READ button any more in normal use (GitHub issue 37). The settings are read by themselves when the meter shows page Ld and every time the page is opened, and the meter's settings cannot change while page Ld is shown; a lit button made it look as if something needed checking. Only when a read fails does a "Read again" button appear, to retry.

New in 1.3.4: updates lose less time on lost answers (GitHub issue 23). Through the two-part bootloader the wait for a missing answer follows how fast the meter has been answering, as TCP does: the average plus four times the variation, at least 1 s, at most 5 s, doubled after each missing answer. Before it was always 20 s; an update with 9 missing answers waited 180 s for them. The wait for the answer to START, which comes once the bootloader has erased the image pages, is 6 s instead of 30 s: the largest image takes 4.8 s to erase at most. The same 6 s apply to the answer to END (the bootloader's check of the written image). On page Ld the wait for an answer is 5 s instead of 20 s; every answer in the reports came within 3.5 s. The "last transfer" line now also says how long START took to be answered. The programs are built with Python 3.15 (was 3.11), bleak 3.1.0 and pywebview 6.2.1.

Also in 1.3.4: the METER SETTINGS page reads the meter's settings by itself (GitHub issue 37). When the meter shows page Ld while the page is open, and every time the page is opened, the settings are read fresh; READ is still there to read them again by hand. Before, only READ did (the automatic read still looked for the page where the settings were before 1.3.1).

New in 1.3.3: a version for Intel Macs (`macos-x86_64`), signed and notarized like the one for Apple chips (GitHub issue 23). Also: the battery type setting of firmware 1.3.4 (F-1.34, GitHub issue 36) in the meter settings list.

New in 1.3.2: the macOS disk image is signed with a Developer ID and notarized by Apple, so it opens like any other app: no "could not verify" question and no trip to Privacy & Security. Every part of the program is signed with the hardened runtime; the disk image carries Apple's ticket, so the check works offline too. The READ ME on the image now has only the install step and the Bluetooth question. Also: the Bluetooth library bleak is updated from 1.1.1 to 3.0.2 on every system (GitHub issue 23). On Windows a connection that Windows could not make within its 7 s ("Could not get GATT services: Unreachable") ended the attempt; bleak now asks again 1 s later, up to 10 times within 30 s, so one such answer no longer costs a whole new search, which the meter's update mode cannot afford.

New in 1.3.1: the meter settings have a page of their own, METER SETTINGS (key 6; the program's own SETTINGS moved to key 7), with the full name of every setting, the meter's page it belongs to ("page 10" instead of "item 10") and every value in words as the meter shows it (GitHub issue 35: the settings were cut to a few letters in a narrow column). A new automatic test renders the page in a browser at the smallest and the common window sizes, in both colour themes, and fails on any cut-off text; it runs on every change. Also: the program connects the moment it hears the meter instead of after a fixed 6 s search, and connects with the device it heard, so Bluetooth does not search a second time (GitHub issue 23, from a Bluetooth capture on Windows); while it waits for the meter to restart into its update mode, which waits only 30 s, it searches again after 0.5 s instead of 3 s and shows no "held by the system" hint. The signal strength in the report is now that of the first advertisement heard. The window "Your meter is offline" can be switched off (SETTINGS, Offline window, or its new button "Don't show again"); the program then keeps searching without asking (GitHub issue 23). Also: the program's events are also written to a file, `events.log` next to the settings file, and the diagnosis report includes the events from before the program was last started (GitHub issue 23: after a failed update the report was empty, because the events were only kept while the program ran). Also: the continuity settings of firmware 1.3.3 (F-1.33). The meter settings list shows and changes your own continuity threshold th (1..500 ohm) and hysteresis HY (0.1..25.0 ohm), and the threshold setting offers the codes 16 DNUSr and 17 UPUSr (beep on a short or on an open at your threshold); the live display names them with the threshold, e.g. "UP 100 Ω". The threshold is read and written with the meter's new two-byte settings requests, which older firmware does not have, so for it these rows are not listed. Fixed: in the continuity function the threshold UP  1 was shown as a dB reading.

New in 1.3.0: link 2 for meters with the old BLE112 Bluetooth module, and packed downloads and updates for every meter (GitHub issue 30). With firmware 1.3.2 (F-1.32) the companion switches the meter to small blocks with repair bytes: settings and serial only when they change, each reading as a difference to the one before, answers first in line; one damaged byte per block is repaired, a lost block costs only its own readings and never shows a wrong value, and the meter's full reading rate gets through. The block pace slows down at once on loss and speeds up after clean time, remembered per meter (measured again after an update). Removed: the per-reading repair of 1.2.33, the error correction of 1.2.35, the speed search of 1.2.36 / 1.2.37 and the link test; meters with older firmware on the old module get the readings as they come and a note to update. Meters with the newer module are not affected. On link 2 the card list, downloads and settings come in the same repaired blocks, in large pieces. Packed (F-1.32 and bootloader 1.1.5): card files are read packed by the meter and unpacked here (log files to about 14 %), and updates are sent packed (the firmware to about two thirds); the meter checks every update as before. Older firmware and bootloaders get the plain transfers; when the companion connects while the meter already shows page Ld (which does not tell its version), it asks for a packed read once and knows from the answer.

New in 1.2.37: the speed search for meters with the old BLE112 Bluetooth module is safer (GitHub issue 30). A speed counts as found only after a full minute in which every reading arrived; any later failure (readings lost, a speed change not confirmed, a stalled link) saves the next lower speed at once, so the next connection does not start at a speed that failed. Speeds saved by an older version of the companion are measured again after an update. While the meter shows page Ld the companion no longer asks its version (the meter cannot answer there); it asks once the page is left.

New in 1.2.36: the companion finds the reading speed each meter with the old BLE112 Bluetooth module can carry (GitHub issue 30). With firmware 1.3.0 (F-1.30) and error correction on, it starts at 7 readings a second, steps down (6, 5, 4, 2) whenever a 10-second window loses readings, and once every reading arrives for 30 seconds it saves that speed for the meter; the next connection starts there. The Meter page shows whether the speed is being tried or found.

New in 1.2.35: readings from meters with the old BLE112 Bluetooth module are corrected (GitHub issue 30). With firmware 1.2.9 (F-1.29) the companion asks the meter to add three repair bytes to every reading and corrects any single damaged byte, also in the digits that change; a reading with two damaged bytes is dropped, never shown wrong. The reading rate on the old module now goes up to 4 a second at most (the module carries about 150 bytes a second). The report shows how many readings were corrected.

New in 1.2.34: the companion says the right way to the meter's page Ld-bt (GitHub issue 34). Since firmware 1.2.2 (F-1.22) that page is one of the meter pages: press SETUP until SEt, hold SETUP until the long beep, then press SETUP until Ld-bt. The update notice and the card view said only "press SETUP until Ld-bt", which never gets there.

New in 1.2.33: damaged readings from meters with the old BLE112 Bluetooth module are repaired (GitHub issue 30). On those meters a byte sometimes arrives shifted by one to three bits; when a reading fails its check because of one such byte, and the byte is one that did not change since the last good reading, the companion puts it back and keeps the reading instead of dropping it. Readings whose changing digits were hit are still dropped, never guessed. The report shows how many readings were repaired. Works with every firmware; firmware 1.2.8 also sends with two stop bits, which should make the damage rarer.

New in 1.2.32: the companion makes sure the computer lets go of the meter after Disconnect (GitHub issue 23). On Windows the meter stayed connected after Disconnect (the tray still showed "Connected (1)"), so it did not advertise and a new Connect found nothing until Bluetooth was switched off and on: the Bluetooth library asks Windows to keep the connection and never takes that back, and leaves the meter's notifications switched on. Disconnect now switches the notifications off, lets Windows drop the link, and checks a few seconds later whether the system still holds the meter. On Linux it then asks BlueZ to end the connection; where no program can end it (Windows keeps a link it insists on, macOS), the status line says what to do: remove the meter in Settings > Bluetooth & devices, or switch Bluetooth off and on. The same check runs when Connect does not find the meter twice in a row. The report shows the result ("system hold"). Also a heartbeat with firmware F-1.26 (GitHub issue 23): while connected the companion sends a one-byte "still here" every 5 s, and the meter switches its Bluetooth module off and on when it hears nothing for 15 s, which frees a connection the computer kept; Disconnect switches this off first. The companion asks the meter when no reading has come for 8 s and reconnects when it does not answer; a meter unreachable for a minute is shown in a window ("Your meter is offline", Keep searching or Stop). Writes to the meter go out one at a time.

New in 1.2.31: the automatic reading rate of meters with the old BLE112 module (firmware F-1.25) aims at no errors (GitHub issue 30): it starts at the lowest rate, 2 a second, goes one step up only after a minute without a single damaged byte, and one step down from 1 % damaged bytes in 10 s. The companion now checks that the meter keeps the rate: Mike's report showed the meter back at its own 20 a second after a few minutes (a restart, a wake or a key on its page bt end the companion's rate), and when far more data arrives than the set rate sends, the rate is set again.

New in 1.2.30: data over Bluetooth adjusts itself to the link (GitHub issue 30). Meters with the old BLE112 Bluetooth module carry about 150 bytes a second. With firmware F-1.25 the companion sets the rate of the readings for the connection itself: it starts at 4 a second, goes one step down when 2 % or more of the bytes in 10 s arrive damaged, and one step up after a minute without a damaged byte, never above the saved bt setting (which is not changed); a rate that fails right after a step up is not tried again in that connection. The meter settings are read in small pieces that shrink until they arrive, as the card list and files already were. Every reading is sent once again: the link tests on two meters showed that the second copy did not help. With older firmware the METER page and the report suggest bt 2 or 4 when the meter sends more than the module carries. The METER page and the report show the rate in use.

New in 1.2.29: the meter settings offer the buzzer's third value "quiet (keys silent)" (GitHub issue 28) for meters with firmware F-1.24 or newer; older firmware keeps the choices off and on.

New in 1.2.28: a link test (GitHub issue 30). "Link test" in Diagnostics on the METER page measures for about a minute whether careful mode's second copy of every reading helps a meter's Bluetooth link or overloads it: the copies on, off, on, off for 15 s each, with the share of damaged bytes and the readings per second of each phase. The meter is set back as before afterwards. The result is shown under the button and goes into the report. Needs firmware F-1.19 or newer and the meter on its readings (not page Ld). A file of your own is installed with one button, "Install file": the program sees from the file whether it is firmware or a bootloader (the two checks exclude each other) and refuses a file that is neither, with the reasons; the buttons "As firmware" and "As bootloader" are gone. Fixed: after an update the notice could stay at "the meter restarts: it starts F-…" although the meter was back with the new firmware: a write that failed while the meter restarted ("BleakError: disconnected") ended the update without a word; now every failed write is handled, and any other error ends the update with its message on the page.

New in 1.2.27: a new look. The reading is drawn as the meter's own seven-segment LCD with its symbols and bargraph (gold on dark glass in the dark theme, black on light glass in the light theme); the pages are cards, chosen in a bar on the left; the top bar shows firmware, bootloader and the status lamps with their names; labels are in normal writing instead of spaced capitals; the whole page scales with the window, at any screen size; LIVE and SCOPE always show whole, also with an update notice above them. On the METER page a table replaces the two release lists: every firmware or bootloader release with newer, installed, older, refused or "connect the meter", and one button each (Install, Reinstall, Go back…); it is read by itself while a meter is connected. A file of your own can be dropped on the page. The theme now follows the computer's light or dark setting by default (System); Dark and Light stay selectable in SETTINGS. SETTINGS shows the program's version ("This program"). Without a meter connected, no release is marked "refused" any more: the list says "connect the meter" (nothing is sent without a meter).

New in 1.2.26: a light theme (GitHub issue 26). SETTINGS has a new choice "Appearance": Dark (as before, the default), Light, or System, which follows the light or dark choice of the computer and changes with it while the program runs. The scope and trend graphs change colours with the page. The choice is kept in the program's settings file and "Reset all settings" returns it to Dark.

New in 1.2.25: the button "Leave Ld-bt" also works while a card operation keeps retrying: it stops that operation first, then takes the meter off the page (before it only said "the link is busy"; GitHub issue 9). The METER view can install any release of the firmware or bootloader, also an older one than the meter has ("Install a version"), and a firmware or bootloader file of your own (GitHub issue 25): going back to an older release and every file of your own first show what can break (the features the newer version added, taken from the project's documents) and need you to type INSTALL; a file is checked like a release image and refused with the reason when it fails (a bootloader file must have the vector table of the two-part bootloader and is sent only to a meter that has it already, because the starter is written once and never again); the transfer is the update's own. The program also shows its own version on the METER view and, at the release check, a notice with a button to the release page when a newer program release exists (GitHub issue 23).

New in 1.2.24: careful mode (old BLE112 module) also adapts the card file list: after an answer that did not arrive it asks for fewer entries per answer (4, 2, then 1) and waits for a lost answer about three times the measured answer time instead of 15 seconds. Four entries with long names, such as the folders a Mac writes on a card, filled a whole answer that a damaging link never delivered, so the list never appeared (GitHub issue 9). Also: on Windows, when the meter cannot be found, the status line says what usually causes it: a meter added in Windows Settings > Bluetooth & devices is kept connected by Windows, so it cannot be found; remove it there and switch the meter's Bluetooth off and on (long PEAK). The companion needs no pairing (GitHub issue 23).

New in 1.2.23: the METER view shows and changes the meter's new setting CHIrP (diode contact chirp, firmware F-1.21 or newer; idea by @Cecilius): on, the diode beep sounds once per diode contact; off, as before. Older firmware does not show the row.

New in 1.2.22: careful mode (old BLE112 module) adapts the size of the card download pieces to the link: it starts at 32 bytes, halves the size after a piece that was lost and doubles it (up to 128) after four in a row that arrived, and waits for a lost piece about three times the measured answer time instead of 5 seconds, so downloads on a damaging link are faster (GitHub issue 20). The report shows the pieces of the last card read by size and how many were sent again.

New in 1.2.21: firmware and bootloader updates work on meters whose Bluetooth connection stays up while the meter restarts into its update mode (meters with the old BLE112 module): the program now asks the meter on that same connection instead of waiting for it to drop, so the meter no longer gives up after 30 seconds and goes back to the old firmware (GitHub issue 21). On Linux the diagnosis report names the distribution (from /etc/os-release).

New in 1.2.20: careful mode for meters with the old Bluegiga BLE112 Bluetooth module (early meters; recognised by the packet size the link negotiates) and firmware F-1.19 or newer: the meter sends every reading twice and the program keeps the copy that checks out, and the card file list and downloads come in small pieces that are asked for again when damaged (GitHub issues 9 and 14). Newer meters are not affected.

New in 1.2.19: the METER view shows and changes the meter's auto power-off time (off, 1, 15, 30 or 60 minutes; firmware F-1.18 or newer, older firmware does not show the row).

New in 1.2.18: with SETTINGS "Extended diagnosis" on and firmware F-1.17 or newer, the report has a section "meter clock": the meter's RC run clock as the meter measured it against its crystal at the last start or wake, after its trim, and the resulting Bluetooth serial speed (GitHub issue 9). The CARD view has a button "Leave Ld-bt" that takes a meter with F-1.17 or newer off page Ld-bt, so the readings come back without touching the meter.

New in 1.2.17: with "Extended diagnosis" on, the meter's link counting is now also switched on after a firmware update (it was refused while the update was finishing, so the report of that connection showed only zeros; GitHub issue 9).

New in 1.2.16: the METER view shows and changes the new meter setting "HUnt" (capacitance anti-hunting) of firmware F-1.16 or newer: with some ceramic capacitors of about 100 nF the capacitance range keeps changing, the digits stay blank and only the decimal point moves; with HUnt on the meter stays on the 1 uF range after two timeouts and shows the value. Off by default; older firmware does not show the row.

New in 1.2.15: more in the diagnosis report (GitHub issue 9: a slow link that damaged data could not be traced). The report has a new section "link details": the last pieces of data the program had to skip as damaged (as hex), how many Bluetooth notifications came, their sizes and the time between them, how long the meter took to confirm what the program sent, the signal strength when the meter was found, the negotiated packet size, why and how often the connection was lost, and how many status frames per second really arrive. Behind a new setting "Extended diagnosis" (SETTINGS, off by default) the program also asks a meter with firmware F-1.15 or newer to count what happens on its own Bluetooth serial line (bytes received, lost bytes, noise, framing errors, rejected commands, battery voltage) and prints the numbers in the report, so the damage can be placed in the meter, on the radio or in the computer. Older firmware is never sent the new commands. The report stays anonymised.

New in 1.2.14: the update check works on macOS again: the program now carries its own list of trusted certificates, so the check no longer fails with "certificate verify failed: unable to get the local issuer certificate" (GitHub issue 13).

New in 1.2.13: "Save report" on the METER view writes a diagnosis report (a text file in the recordings folder) to attach to a GitHub issue instead of a screenshot: versions, the link, the last transfer, the firmware's diagnosis, the meter's settings and a log of what happened since the companion started (connections, version and bootloader questions, page Ld, updates, card operations). It is anonymised: no Bluetooth ID or address, no computer or user name, no file paths, no time zone.

New in 1.2.12: the diagnosis text on the METER view is shown in full instead of in a short box that had to be scrolled (GitHub issue 12).

New in 1.2.11: the firmware version is asked up to three times after connecting before a meter is taken for EEVblog's v2.05 (a lost answer showed "F-2.05 / LIKE" for a meter with F-1.12, and the CARD view, the meter's settings and the update check were off for that connection).

New in 1.2.10: the same as 1.2.9 (whose Windows build stopped at a test that assumed a finer clock than Windows has).

New in 1.2.9: after a firmware or bootloader transfer the companion shows what the time went on: packets sent again, answers that did not come and the time waited for them, damaged packets, the slowest answer (in the update notice and as "last transfer" on the METER view; GitHub issue 9). An update through the two-part bootloader no longer stops with "packet N: accepted" when one answer of the meter was lost (GitHub issue 11).

New in 1.2.8: the bootloader of the meter is asked up to three times after connecting, and again before an update chooses its route (one lost answer showed "B-—" for the whole connection, so the bootloader update was not offered and a firmware update could take the card route; GitHub issue 10); the local server answers a malformed request at once instead of holding a thread (GitHub issue 8).

New in 1.2.7: a SETTINGS view (key 6) for the program's own settings: the recordings and card sync folders, the CSV format of recordings (comma-separated with a decimal point, or semicolon-separated with a decimal comma for spreadsheets that expect one), the time server and setting the meter's clock after each connection, how often to look for new firmware and bootloader releases (on connect, daily, never), diagnostic logging, and a reset of all of them. The time server moved there from the METER view, where "Sync time" stays.

New in 1.2.6: the CARD view says "no files on the card" only once the meter has answered the listing; until then it shows "reading the card…" (GitHub issue 7: an unanswered listing looked like an empty card).

New in 1.2.5: the METER view's diagnosis shows the write-timeout values of firmware F-1.11 (which part of a card write timed out, for how long, what the card answered); older firmware shows the values it has.

Fixed in 1.2.4: a format refused by a meter whose firmware is older than F-1.09 says so (it said "not allowed now"); formatting a large card works with firmware F-1.10 (a slow card write stopped the format).

New in 1.2.3: "Format card" in the CARD view (meter on the page Ld-bt, firmware F-1.09 or newer with the two-part bootloader): type FORMAT to confirm, a window stays open until the meter has formatted the card.

Fixed in 1.2.3: buttons answer the first click on macOS (Connect needed up to ten clicks, the update notice's button did not answer: the page rewrote the button text on every redraw, and WebKit drops a click whose pressed text was replaced); the CARD view shows the card's space (two requests sent together refused the second); the LOG view lists the recordings folder with size and date; the update notice says where the meter restarts to.

Fixed in 1.2.2: the Windows installer asks for administrator rights at start and installs for all users into Program Files (before it installed into the user's AppData folder and could fail); an earlier per-user copy is removed first. Without administrator rights, start the installer with /CURRENTUSER. The .sha256 file of the Windows installer ends its line with LF, so sha256sum -c / shasum -c accept it.

Fixed in 1.2.1: Connect works on the first click (macOS: the window is brought to the front at start; a Connect right after a Disconnect starts a new search; a search stopped half-way leaves no half-open connection behind, which kept the meter from being found); the button shows Connect / Stop searching / Disconnect; the update check shows "up to date" with the newest releases and the time of the check, or why it failed; versions shown once (F-1.05, not F-F-1.05).

New in 1.2.0: five views (LIVE, SCOPE, LOG, CARD, METER) in a new bench-instrument design; derived values (REL %, loop %, Pt100 / Pt1000, own limit test); the meter's keys from the computer; the SD card from the computer (list, download, delete, sync to a folder) and the meter's settings, both with firmware F-1.05 or newer on the page Ld-bt; the diagnosis values.  Verified working on a meter: card list, a 169 KB download equal to the file on the card, settings read and changed.
